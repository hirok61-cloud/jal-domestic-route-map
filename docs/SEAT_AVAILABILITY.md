# 空席状況（`/seats/`）の作り方

羽田発着の主要35路線（往復70区間）について、JAL公式の空席照会と同じデータを
**今日と翌日の2日分**を保持する。座席表まで見るため
**1日あたり空席照会70回＋座席表約345回で8〜10分**かかるので、
更新は**日を選んで実行する**（両日まとめると20分近くになる）。

- サイトの更新ボタンは、いま見ている搭乗日タブの日だけを取り直す
  （ラベルも「今日分を更新」「明日分を更新」と変わる）
- ブックマークレットは実行直後に「今日 / 明日 / 両日」を聞く
- 依頼は `jal_seat_requests.day_offsets`（0=今日, 1=翌日）で運ばれ、
  `?action=claim` が `job.days` として収集側に渡す
表示先は2か所:

- `/seats/` — 区間ごとの便一覧（便名・時刻・機材・残席・最安運賃）。
  上部の「搭乗日」で今日／明日を切り替える。今日の便が残っていない時間帯は
  自動的に翌日を開く
- `/`（ルートマップ）— **今日分のみ**。サブタブ横の「空席で塗り分け」ボタンで、地図の路線を
  空席あり=緑／残りわずか=橙／満席=灰／全便欠航=赤破線 に塗り替える。
  対象外（羽田発着以外）の路線は薄く表示する。

## 更新のやり方

やり方は2通り。どちらも git 操作やファイル移動は要らない。

**方法1: サイトのボタン（PCにChrome拡張を入れておく）**

`/seats/` で搭乗日タブ（今日／明日）を選んでから更新ボタンを押す。
ボタンには「今日分を更新」「明日分を更新」と対象が出る。選んだ日だけを取り直す。
実際の収集はMacのChrome拡張が拾って行うので、**PCが起きている必要がある**。
寝ていると3分で「Macが起動していなかったため実行されませんでした」になる。

**方法2: スマホのブックマークレット（PCが寝ているとき）**

初回だけ <https://jal-domestic-route-map.vercel.app/seats/update.html> で
合言葉を入れ、ブックマークに登録する。以降は:

1. [JAL公式サイト](https://www.jal.co.jp/ja-jp/)を開く（検索は不要）
2. 登録したブックマークレットを呼び出す
3. 30秒ほどで空席照会の画面に切り替わるので、**もう一度**呼び出す
4. 「今日 / 明日 / 両日」を聞かれるので選ぶ

送信に失敗した場合は `availability.json` が自動でダウンロードされるので、
`data/availability.json` に置いて push すれば従来どおり反映できる。

### スマホから更新する

スマホにはブックマークバーがないので、**ブックマークを1つ作ってURLを差し替える**。
`update.html` は端末を判定して手順を出し分けるので、そちらを見れば足りる。要点だけ:

- **iOS Safari**: 共有 →「ブックマークを追加」→ ブックマーク一覧の「編集」で
  URL欄に貼り付け。実行はブックマーク一覧からタップする。
  `javascript:` をアドレスバーに貼っても Safari は実行しない。
- **Android Chrome**: ブックマークを作って名前を `jalseat` のような短い語にし、
  URL欄に貼り付け。実行はアドレスバーに `jalseat` と入力して候補をタップする。
  アドレスバーに直接貼ると Chrome が `javascript:` を削除してしまう。

収集中はその画面を開いたままにする必要がある。ほかのアプリに切り替えたり画面が
消えるとタイマーが絞られて取りこぼすため、収集スクリプトは Screen Wake Lock API で
画面スリープを抑止し、`visibilitychange` で画面が消えたことを検知して
失敗時のメッセージに添える。

## 構成

```
JALの予約画面（人が開いたブラウザ）
  ├─ ブックマークレット（<script>タグで読み込む。配信元を3つ順に試す）
  │    └─ seats/collect.min.js               ← 生成物
  └─ Chrome拡張（executeScript で注入）
       └─ extension/collect.js               ← 生成物
     どちらも中身は tools/collect-core.js（収集ロジックはこの1本だけ）
            ├─ api.dom.jal.co.jp …… 70区間分空席照会
            └─ POST supabase/functions/v1/jal-seats （x-update-key 付き）
                 └─ public.jal_seat_snapshots（hubごとに1行を上書き）

サイト（/seats/ と /）
  └─ GET supabase/functions/v1/jal-seats   ← ふだんはこちら
       └─ 失敗したら data/availability.json（コミット済みの静止データ）
```

- Supabase プロジェクト: `xymbknvwllwhmqlexege`
- Edge Function: `jal-seats`（`verify_jwt=false`。GETは公開、POSTは合言葉必須）
- テーブル: `public.jal_seat_snapshots`（RLS有効・匿名SELECTのみ許可。書き込みは
  Edge Function が service role で行う）
- **合言葉はこのリポジトリに置かない。** ブックマークレット（＝利用者のブラウザ）
  だけが持ち、`window.__JAL_SEATS_KEY` として収集スクリプトに渡す。
  置き場所は Edge Function の環境変数 `JAL_SEATS_UPDATE_KEY` だけ。
  **未設定なら書き込みを全部拒否する**（黙って既定値に戻らない）。
  コミット前に `npm run check:secrets` が見張っている。

## なぜブラウザ上で収集するのか

- `jal.co.jp` / `booking.jal.co.jp` は **Akamai Bot Manager** 配下で、
  `curl` は 403、Vercel のサーバ関数からも 403。
- 空席API `api.dom.jal.co.jp/rmweb-api/search/air-bounds` は
  `Access-Control-Allow-Origin: https://booking.jal.co.jp` 固定なので、
  ブラウザからは予約サイトのページ上でしか呼べない。
- Playwright / Selenium で起動した Chrome は Akamai に検知され、
  **JALのアプリ自身のAPI呼び出しごと失敗する**（実測）。CDP接続でも同じ。
- さらに、トップページにフォームPOSTしただけのセッションは 429（`cpr_chlge`）で
  弾かれる。**検索ウィジェットを実際に操作して作ったセッション**でないとAPIが通らない。
- 結局、人が普通に開いたブラウザのセッションを間借りするのが、いちばん確実で
  JAL側への負荷も小さい（1巡70リクエスト・1.2秒間隔）。

## データ仕様

Edge Function が返す JSON（`data/availability.json` と同じ形）

| フィールド | 内容 |
|---|---|
| `generatedAt` | 取得時刻（ISO8601） |
| `date` | 搭乗日 `YYYY-MM-DD` |
| `hub` | ハブ空港コード（`HND`） |
| `routes[]` | 区間ごとの結果。`o`=出発, `d`=到着, `status` |
| `routes[].status` | `ok` / `cancelled`（全便欠航） / `empty`（残り便なし） / `error` |
| `routes[].flights[]` | 便ごとの空席 |

便レコード:

| キー | 内容 |
|---|---|
| `no` | 便名（`JL117`） |
| `op` | 運航会社コード（`JL` / `NU` など） |
| `dep` / `arr` | 出発・到着時刻 `HH:MM` |
| `ac` | IATA機材コード（`359` / `788` / `73H` など） |
| `eco` | **普通席の残席数** |
| `clsj` | クラスJの残席数（`null`=設定なし） |
| `first` | ファーストクラスの残席数（`null`=設定なし） |
| `fare` | 普通席で購入可能な最安運賃（円・大人1名） |
| `sa` | **座席表で実際に指定できる普通席の数**（運賃が空席ありの便のみ） |
| `st` | 普通席の総座席数 |
| `sw` / `sl` / `sc` | そのうち窓側 / 通路側 / 中央の数（座席属性コード `W`+`1W` / `A` / `9`） |
| `se` / `sg` | そのうち非常口席 / 足元が広い席の数（`E` / `L`） |
| `sm` | **空いている普通席の一覧**（2026-08-09 追加。下記） |
| `sj` / `sf` | クラスJ / ファーストの座席表の空き（設定のない機材は `null`） |
| `pe` / `ps` | **前回の収集時**の `eco` / `sa`。保存時にサーバ側が付ける |

トップレベルには前回の収集時刻が `prevAt` として入る。

**残席数は 9 が上限**。JALは10席以上あっても `quota: 9` としか返さないので、
サイトでは `9` を「空席あり」、`1〜8` を「残りN席」、`0` を「満席」と表示する。

**運賃の在庫（`eco`）と座席表（`sa`）は別物。** 予約クラスの枠が空いていても、
JALが当日空港割り当て分の座席を確保しているため、座席表側は埋まっていることがある。
実測例: 8/10 JL101 羽田→伊丹 は運賃上「空席あり」だが、座席表では普通席227席中
選べるのは17席（使用済み198・ブロック12）だった。サイトは普通席バッジの下に
「座席表 17席」／「座席表は満席」と併記する。

出発済みの便はAPI側で除外されるため、`flights[]` は常に「これから出発する便」だけ。

## 取得ロジックの要点

- 空席照会は1区間1回。`itineraries` に片道1本だけ入れる。
- 座席表は `POST rmweb-api/shopping/seatmaps` を**1便1回**。
  `bookingClass` は必須だが `"Y"` 固定でよい（運賃別の `"A,U,T"` と結果が一致した）。
  返ってくる `data.seatmaps[0].decks[].seats[]` の `cabin==="eco"` を数え、
  `travelers[0].seatAvailabilityStatus === "available"` を空席とする
  （ほかに `occupied` / `blocked` がある）。
  レスポンスが1件あたり約108KBと大きいので、**運賃が空席ありの便だけ**に絞る。
  それでも2日分で約690便・約70MB・15分ほどかかる。
- `searchPreferences.showSoldOut: true` を付けて満席便も返させ、こちらで判定する。
- レスポンスの `availabilityDetails[].statusCode` は `HK`=確保可 / `HL`=キャンセル待ち。
  ただし**「対象者限定」の運賃ファミリーは満席の便でも `HK` かつ `quota: 0` を返す**ので、
  空席の有無は `statusCode` ではなく **`quota` の最大値**で判定すること。
- `boundDetails.segments` が2本以上の旅程（乗り継ぎ）は対象外。
- セッションは `booking.jal.co.jp` の `sessionStorage.apiAuthCreds.authToken`
  （有効約2時間）＋ 予約サイトのバンドルに埋まっている `x-api-key`。

## 対象路線を変えるとき

`tools/collect-core.js` の `SPOKES` 配列を編集し、`npm run build:bookmarklet` して push。
ブックマークレットは毎回このファイルを読みに行くので、登録し直す必要はない。
区間を増やすとその分JALへのリクエストが増えるので、`DELAY_MS` は短くしないこと。


## 注意している点（ハマりどころ）

- **夜間は全区間が `cancelled` で返る。** 最終便まで出発済みだとJALは
  「Flights Scheduled but all are cancelled」を返すので、台風などの欠航と
  区別がつかない。全国どこ行きも一斉に欠航することは実際にないので、
  *全区間が cancelled かつ当日* なら「本日の運航は終了」として表示する。
  収集側も、これを失敗と誤判定しないよう **全区間が `error` のときだけ**
  セッション拒否とみなして保存を見送る。
- **ブックマークレットは `<script>` タグで `collect.min.js` を読み込む。約2,500字。**
  ここは3回作り直している。経緯を残しておく。

  1. 収集ロジックを丸ごと埋め込む方式 → 20,332字になり、**Androidのブックマークで
     切り捨てられて何も起きなくなった**（実測）。日本語は1文字が `%XX` 表記で
     9字に膨らむため、UI文言だけで嵩む。
  2. `fetch` で取ってきて `eval` する方式（約800字）→ 実行はされるが、Androidで
     **「収集スクリプトを取得できませんでした」から先に進まなかった**。
     `fetch` はレスポンスに `Access-Control-Allow-Origin` が要るので、
     途中の機器やボット対策がヘッダを落とすと `Failed to fetch` になる。
     取ってきた中身を `eval` する必要もあり、詰まりどころが2つある。
  3. **いまの方式**。`<script>` タグなら CORS も `eval` も要らない。
     配信元を Vercel → jsDelivr → GitHub Pages の順に試し、どれか1つ届けば動く。
     中身はどれも同じ `seats/collect.min.js`。

  なお **jal.co.jp / booking.jal.co.jp は CSP を出していない**（両方とも
  `content-security-policy` なし。実測）。`eval` が禁じられていたわけではない。

- **「読み込めたか」は `window.__JAL_SEATS_BOOTED` で判定する。**
  収集スクリプトの先頭で同期的に立てている。`<script>` の `load` は中身の実行後に
  鳴るので、鳴った時点で立っていなければ「届いたが動かなかった」と分かり、
  次の配信元へ進める。合わせて進捗枠（`#jal-seat-collector`）の有無も見ており、
  CDNに目印のない古い版が残っていても二重起動しない。
- **収集ロジックを直したら、必ず作り直すこと。**

  ```bash
  npm install          # 初回だけ
  npm run build:bookmarklet
  ```

  `tools/collect-core.js` から `seats/collect.min.js`（ブックマークレット用）と
  `extension/collect.js`（拡張用）を再生成する。生成物もコミットする。
  あわせて `npm run test:collect` を通す（両方の外側を同じシナリオにかける）。
  読み込み方式なので、**利用者の登録し直しは不要**（ブックマークレット自体を
  変えたときだけ必要）。
- **動作テスト用の極小ブックマークレット**を `update.html` に用意してある。
  枠が出るか／どのホストで動いたかで、原因が「呼び出し方」なのか
  「Chromeがブックマークレットを実行できない」のかを切り分けられる。
- **Androidでの実行はアドレスバー経由。** JALの画面でアドレスバーに `jalseat`
  と入力し、出てきたブックマークの候補をタップする。ブックマーク一覧から開くと
  現在のページではなく新規タブで動いてしまう。
- **スナップショットは (hub, 搭乗日) で1行。** 過去日は
  `jal_prune_old_snapshots()` が掃除する（`?action=all` のたびに走る）。
- **1回の収集は2回保存する**（運賃だけ→座席表を足して再保存）。そのため
  「前回の値」を素直に付けると2度目で自分自身を参照してしまう。収集側が
  `runId` を送り、同じ収集の2度目なら前回分を引き継ぐようにしている。
  履歴も `run_id` で上書きし、1回の収集につき1点に保つ。
- **窓側/通路側は座席属性コードで数える。** 2026-08-09、実データ2,900席で確定した。
  席の位置は **`A`(通路) / `9`(中央) / `W`(窓) / `1W`(窓の一種)** の4つで表され、
  **この4つに過不足なく分かれる**（合計が数えた空席数とぴったり一致）。
  取りこぼしている属性はない。

  | コード | 件数 | 割合 |
  |---|---|---|
  | `A` 通路 | 1,317 | 45.4% |
  | `9` 中央 | 1,269 | 43.8% |
  | `W` 窓 | 281 | 9.7% |
  | `1W` 窓 | 33 | 1.1% |

  `1W` も窓である裏付け: `LS`(左側)+`RS`(右側)=314 が `W`+`1W`=314 と一致する。
  以前 `1W` を数えていなかったため、**窓側を約1割少なく出していた**（修正済み）。

- **「空席のうち窓側が少ない」のは不具合ではない。** 窓側から先に売れるため。
  かつて「中央席は座席配置上33%が上限なのに43%ある」＝取りこぼし、と判断したが、
  これは**空席に占める割合と全座席に占める割合を比べていた誤り**だった。
  実データでは空席率が上がるほど窓側の割合も上がる。

  | 空席率 | 便数 | 窓 | 通路 | 中央 |
  |---|---|---|---|---|
  | 0〜10% | 90 | 7.1% | 32.7% | 60.2% |
  | 10〜20% | 38 | 8.8% | 40.6% | 50.6% |
  | 20〜35% | 13 | 8.6% | 53.9% | 37.6% |
  | 35〜50% | 6 | 12.6% | 61.8% | 25.6% |
  | 50%以上 | 1 | 26.5% | 35.3% | 38.2% |

- **非常口席・足元の広い席は `se` / `sg` として数えている**（2026-08-09 実装）。
  サイトの「座席」で、窓側・通路側・非常口・足元ゆったりが空いている便に絞り込める。

  | コード | 件数 | 意味 |
  |---|---|---|
  | `E` | 255 | 非常口席。**同じ255席に `1A`（乳幼児不可）が付く**ので裏付けになる |
  | `L` | 264 | 足元が広い席 |
  | `K` | 52 | バルクヘッド（区画の最前列） |
  | `H` | 17 | 身体の不自由な方向け |
  | `LS`/`RS` | 150/164 | 左側／右側（窓側の席にだけ付く） |
  | `ES` | 2,900 | 全席に付く。普通席であることの印 |
  | `EC`/`X`/`SC`/`1D`/`V`/`I2`/`FC`/`NM`/`O` | 37〜708 | 意味未確認 |

- **コードは `travelers[0].seatCharacteristicsCodes` にしかない。**
  `seats[].seatCharacteristicsCodes` は存在しない（実測で空）。読む場所はこれで正しい。
  座席オブジェクトが持つのは `cabin` / `seatNumber` / `travelers` / `blockId` /
  `seatType` / `coordinates` / `equipment`。**`seatNumber` と `coordinates` があるので、
  座席表そのものを描くこともできる。**
- **自動更新は朝7時に今日分、夜21時に明日分**（拡張の設定でON/OFF）。
  21時には今日の便がほぼ終わっているため、夜は翌日を取る。Macが寝ていた場合は
  起きたあとに発火するが、直近6時間以内に自動更新していれば見送る。

## 座席の種類での絞り込み

`/seats/` のフィルタバーに「座席」がある。窓側 / 通路側 / 非常口 / 足元ゆったりの
いずれかが**1席以上空いている便**だけを表示する。値はそのまま便レコードのキー
（`sw` / `sl` / `se` / `sg`）になっている。

- 追加のリクエストはゼロ。すでに取っている座席表の応答を数え直しているだけ
- **座席表をまだ見ていない便は絞り込みに出てこない**。その席が空いているか
  分からないため。座席表は「運賃が空席あり」の便だけ見るので、満席便は該当しない
- 中央席（`sc`）は `sa - sw - sl` でも出せるので、サーバ側が前回の値を引き継いだ
  古い形のデータでもサイト側で補って表示する

**Edge Function の `SEAT_KEYS` には `sc` / `se` / `sg` を足していない。**
足せば、座席表を取り直していない便でも前回の値を引き継げるが、本番にデプロイ
されている版はリポジトリの版と細部が違っており（`?action=script` の書き方）、
リポジトリからそのままデプロイすると差分が巻き戻る。触るときは
`get_edge_function` で本番を取って突き合わせてから。

## 座席表の詳細（クリックで席番号を見る）

`/seats/` の普通席セル（「空席あり」「残りN席」）は、座席の一覧を持っている便では
クリックできるボタンになる。押すと、**空いている座席番号を行ごとに並べたモーダル**
が開く。窓側/通路側/非常口・足元ゆったりを色分けする。

**追加のJALへの問い合わせはない。** 座席表を取るときの応答に元から
`seatNumber`（席番号）が入っており、いままでは数えるだけで捨てていた。
それを持ち帰るようにしただけ。

### `sm` の形式

便レコードの `sm` は文字列の配列。**空いている普通席だけ**を持つ（満席の便は
`sm: []`）。1件は `"席番号"` または `"席番号:属性"`。

```
"15D"      → 15D（属性なし＝中央席）
"15H:WE"   → 15H、窓側(W)かつ非常口(E)
```

属性は1文字ずつ詰める。`W`=窓側（`1W`も含む）、`A`=通路側、`E`=非常口、`L`=足元ゆったり。
`sc`/`se`/`sg` の集計と同じ判定なので、数える元は同じ。

### 割り切っていること

- **埋まっている席の位置は持たない。** 「どの席が空いているか」だけが目的で、
  「機内全体の埋まり方」を再現する座席図ではない。満席の席をグレーで敷き詰める
  ような本物の座席表は作っていない（そのためには使用済み・ブロック席の
  座席番号も持ち帰る必要があり、データ量が数倍に増える）
- **クラスJ・ファーストは対象外。** `sm` は普通席のみ
- **鮮度は座席表の残りと同じ**（`saAt` があればその時点、無ければ収集時刻）。
  実際に予約しようとした時点で埋まっていることは普通に起きる。モーダルの
  注記にも明記している
- **`sm` もサーバ側で前回の値を引き継がない**（`sc`/`se`/`sg` と同じ理由）。
  運賃だけ先に保存した直後（座席表を取り直している最中）は、その便の
  クリックが一時的にできなくなる。次の区切り保存（50便ごと）で戻る

### データ量

1席あたり約3〜7字（`"15D"` 〜 `"15H:WE"`）。2026-08-09時点の実データ
（空席あり便453便・空席合計11,785席）で試算すると、全体のデータは
約96KBから約177KBに増える見込み（実測ではなく試算）。Edge Function の
上限（`MAX_BODY` 2MB）には遠く届かない。
