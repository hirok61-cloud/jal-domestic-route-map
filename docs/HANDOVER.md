# 引き継ぎメモ（空席状況まわり）

2026-08-09 時点。ルートマップ本体（`index.html` / `international/`）は以前から動いている
ものなので、ここでは **2026-08-08 以降に足した「空席状況」機能**についてまとめる。

---

## 1. 何を作ったか

JAL国内線の**羽田発着35路線（往復70区間）**について、当日と翌日の空席をまとめて見られる
ようにした。JAL公式で1区間ずつ調べる手間をなくすのが目的。

| 場所 | 内容 |
|---|---|
| <https://jal-domestic-route-map.vercel.app/seats/> | 便ごとの一覧。搭乗日（今日／明日）、方向、空席あり/満席のみ/全便、空港名で絞り込み |
| <https://jal-domestic-route-map.vercel.app/> | ルートマップ。「空席で塗り分け」ボタンで路線を空席状況の色に変える（**今日分のみ**） |
| <https://jal-domestic-route-map.vercel.app/seats/update.html> | 更新のやり方・ブックマークレットの設定 |

表示している数字は2種類ある。**この2つは別物**なのが要点。

- **運賃の在庫**（`eco`）… 予約クラスの枠。JALは9が上限で、10席以上でも9としか返さない。
  サイトでは `9`→「空席あり」、`1〜8`→「残りN席」、`0`→「満席」
- **座席表**（`sa`）… その便で実際に指定できる普通席の数。JALが当日空港割り当て分を
  確保しているため、**運賃が「空席あり」でも座席表は満席**ということが普通に起きる。
  同じ座席表から窓側/通路側（`sw`/`sl`）、クラスJ/ファースト（`sj`/`sf`）も数えている

## 2. なぜこんな構成なのか（先に読むと事故らない）

JALの空席は**人が開いたブラウザの中からしか取れない**。ここが全ての制約の源。

- `jal.co.jp` / `booking.jal.co.jp` は **Akamai Bot Manager** 配下。`curl` は 403、
  Vercelのサーバ関数からも 403
- 空席API は `Access-Control-Allow-Origin: https://booking.jal.co.jp` 固定。
  ブラウザからでもJALの予約サイトのページ上でしか呼べない
- **Playwright / Selenium で起動した Chrome は検知される**。CDP接続でも同じで、
  JALのアプリ自身のAPI呼び出しごと失敗する（実測）
- トップページにフォームPOSTしただけのセッションも 429（`cpr_chlge`）で弾かれる。
  **検索ウィジェットを実際に操作して作ったセッション**でないとAPIが通らない

→ 結論として「人のブラウザのセッションを間借りして、結果だけサーバに送る」形にした。

```
JALの予約画面（人のブラウザ）
  ├─ Chrome拡張（Mac常設）… サイトのボタン／自動更新から動く
  └─ ブックマークレット（スマホ用）… Macが寝ているとき
        │
        ├─ api.dom.jal.co.jp で空席照会（70区間）＋座席表（空席のある便ぶん）
        └─ POST → Supabase Edge Function `jal-seats`
                      └─ public.jal_seat_snapshots （hub, 搭乗日 で1行）
                         public.jal_seat_history   （推移。7日保持）

サイト（/seats/ と /）
  └─ GET Edge Function → 失敗したら data/availability.json（コミット済みの静止データ）
```

### Supabase

プロジェクト `xymbknvwllwhmqlexege`。

- Edge Function `jal-seats`（`verify_jwt=false`）
- テーブル `jal_seat_snapshots` / `jal_seat_history` / `jal_seat_requests`
- 関数 `jal_expire_stale_requests` / `jal_prune_old_snapshots` / `jal_prune_old_history`

**書き込み用の合言葉**は `x-update-key` ヘッダ。**置き場所は Supabase の環境変数
`JAL_SEATS_UPDATE_KEY` だけ**で、リポジトリには一切置かない。
持っているのはブックマークレット（URLに埋め込まれる）と拡張（`chrome.storage.local`）。

- **未設定なら書き込みを全部拒否する**（fail closed）。以前は「環境変数が無ければ
  既定値を使う」と書いてあり、その既定値がソースに直書きされたまま public リポジトリに
  push されていた。2026-08-09 に発覚し、合言葉を入れ替えた
- `npm run check:secrets`（`tools/check-secrets.mjs`）がコミット前に見張る。
  **照合はハッシュで行い、値そのものはどこにも書かない。** ハッシュの一覧は
  追跡しない `.secret-hashes`（.gitignore 済み）。新しい端末では
  `printf '%s' '合言葉' | node tools/check-secrets.mjs --add` で作る
- `.git/hooks/pre-commit` に仕掛けてある（フックは追跡されないので端末ごとに入れ直す）
- **合言葉を変える順番**: ①Supabaseの環境変数を新しい値にする →
  ②拡張のオプションを貼り替え → ③`/seats/update.html` でブックマークレットを
  作り直して登録し直す（合言葉はURLに埋め込まれているので再登録が必須）。
  ②③のあいだ更新は「合言葉が違います」で弾かれるが、収集は手動なので実害はない

| `POST /` | スナップショット保存（合言葉必須） |

## 4. 更新のしかた

**1日分あたり8〜10分**かかる（空席照会70回＋座席表 約345回＝約415リクエスト、約35MB）。
そのため**日を選んで実行する**。両日まとめると20分近くになる。

### 方法1: サイトのボタン（Chrome拡張が要る）

`/seats/` で搭乗日タブを選ぶ → ボタンが「今日分を更新」「明日分を更新」に変わる → 押す。
実際の収集はMacのChrome拡張が拾って行うので、**Macが起きている必要がある**。
寝ていると3分で「Macが起動していなかったため実行されませんでした」になる。

拡張の入れ方: `chrome://extensions` →デベロッパーモードON→「パッケージ化されていない
拡張機能を読み込む」→ `extension/` フォルダ → 拡張のアイコンから合言葉を貼る。

**自動更新**（拡張の設定でON/OFF）: 朝7時・昼12時に今日分、夜22時に明日分
（2026-08-10、朝夜2回から3回に変更）。22時には今日の便がほぼ終わっているため
夜だけ翌日を取る。Macが寝ていた場合は起きたあとに発火するが、直近4時間以内に
自動更新していれば見送る（枠の間隔が最短5時間＝朝→昼なので、見送りの閾値は
それより短くしないと正常運転でも毎回スキップされる。`extension/background.js`
の `AUTO_MIN_GAP_MS`）。

**2026-08-23確認: このMac（MacBook Air）はシステムスリープが1分に設定されている
（`pmset -g custom` の `sleep`。AC電源時・バッテリー時とも）。** ディスプレイ
スリープ（10分）とは別物で、こちらが効くとChrome自体が止まり、
`chrome.alarms` は次にMacが起きるまで発火しない。つまり**朝7時・昼12時・夜22時に
Macを操作していない限り、その回はほぼ確実にスリープ中で、起きたときに
まとめて発火（→直近4時間ガードで一部見送り）というのが実態**。
本人に確認のうえ、**この設定は変えない方針**（2026-08-23）。
自動更新の抜けが気になったときは、まずここを疑うこと。
変えるなら `sudo pmset -c sleep 0`（AC電源時のみ無効化）。

### 方法2: スマホのブックマークレット（Macが寝ているとき）

`/seats/update.html` で合言葉を入れて生成→ブックマークに登録。
JALのサイトを開いた状態で呼び出すと、30秒ほどで空席照会画面に進むので**もう一度**押す。
「今日 / 明日 / 両日 / 制度枠（今日）」を聞かれるので選ぶ
（制度枠はJALオンライン専用。`docs/JAL_ONLINE_CORP.md` 参照）。

- **iOS**: ブックマーク一覧（本のアイコン）からタップ
- **Android**: アドレスバーに `jalseat` と入力して**候補をタップ**
  （ブックマーク一覧から開くと新しいタブで動いてしまい失敗する）

## 5. ハマったところ（同じ罠を踏まないために）

- **JALの静的コンテンツの版（`contentVersionId`）は書き写さない。ページから借りる**
  （2026-08-28に直した）。JALは不定期にこの版を上げ、**古い版を渡されると
  seatmap API が HTTP 200 のまま**
  `{"errors":[{"code":"JSLCMNE002","title":"404 Not Found on GET request for
  \".../content/1.0.171/assets/…\""}]}` を返す。`seatmap()` は status しか見て
  いなかったので、これが「その便は座席表なし」として静かに処理されていた。
  **同じ事故が2回起きている**（2026-08-15の 1.0.170→1.0.171、
  2026-08-28の 1.0.171→1.0.175）。運賃側（air-bounds）は古い版でも黙って通るため、
  運賃だけ正常に見えて発見が遅れるのが毎回同じ。
  - JALのSPAは、いま使っている版を **`<body data-dynamiccontentpath="…">`** に
    持っていて、アプリ自身が送っている `contentVersionId` はこの値そのもの
    （2026-08-28、ページの `fetch` を覗いて一致を確認）。収集はそのページの中で
    動くので、`detectContentVersion()` がここから借りる＝JALが上げても追随する。
    `CONTENT_VERSION_FALLBACK` は属性が読めなかったときの控えでしかない
  - **切り替えは段階的に来る**。8/26夜から座席表の取得数が 308→89→48→0 と
    数日かけて減った（古い版がまだ残っているサーバに当たったぶんだけ成功していた）。
    「全滅」だけを見張っていると数日気づけないので、`?action=recent` の
    「座席表確認 N便」が**空席便数よりはっきり少ない**日が続いたら疑う
  - 版ずれは3便続いた時点で見切る（以前は300便ぶん・約11分を空振りしてから
    失敗していた）。スナップショットには `contentVersion` を入れてあるので、
    後から「いつどの版で集めていたか」が分かる
- **収集ロジックは `tools/collect-core.js` の1本だけ**。以前はブックマークレット用と
  Chrome拡張用に**同じロジックのコピーが2つ**あり、片方だけ直して片方が置き去りに
  なった。2026-08-09、直したはずの中断処理も座席属性の調査も拡張には入っておらず、
  拡張経由で集めた結果に材料が入っていなくて1往復むだにした。
  いまは本体1つ＋外側2つで、`extension/collect.js` も生成物
- **収集ロジックを直したら `npm run build:bookmarklet` を必ず実行**。
  `seats/collect.min.js` と `extension/collect.js` は生成物で、これも一緒にコミットする。
  あわせて **`npm run test:collect`**（`tools/simulate-collect.mjs`）を通す。
  偽のブラウザと偽のJAL・保存先の上で収集スクリプトを実際に走らせて、
  完走／JALに弾かれたとき／保存が失敗したときの分岐を確かめる。外部へは一切つながない
- **JALに弾かれたら3区間で止める**。以前は70区間を叩ききってから
  「全区間 error」で失敗しており、90秒待たされたうえJALにも70回の無駄打ちをしていた。
  1区間も取れないまま3区間続いたら、その場で理由（`Failed to fetch` か `HTTP 403` か）
  とやり直し方を出して止める
- **`fetch` が例外を投げるのとHTTPエラーは原因が別**。例外はCORSヘッダの付かない応答
  （＝Akamaiの遮断ページ）か通信断で、HTTPエラーはJALが返事はしている状態。
  区別して表示しないと切り分けができない
- **一部の端末は保存先のドメインごと遮断される（2026-08-14、実機での完全解決を確認済み）**。
  実機2台（Android・別のiPhone）で「70区間は取れるのに保存だけが必ず失敗する」状態を確認。
  **Supabase側のログでも、その時間帯（22:48〜23:15 JST）にPOSTが1件も届いていない。**
  JALのAPIは同じ `jal.co.jp` なので通り、第三者ドメインの `supabase.co` だけが落ちる。
  **`fetch` を XHR に変えても宛先が同じなら同じように弾かれる**ので、手段の追加では直らない。
  実機で `fetch blocked by privacy-gateway`（ただの文字列＝JS層で`fetch`が
  差し替えられている証拠）も確認済み
  - **このサイト（`jal-domestic-route-map.vercel.app`）経由の中継は置けない。**
    Vercel が GitHub Pages を中継しているだけで（応答に `x-github-request-id` が付き、
    POSTは405、`/api/save.js` は静的ファイルとして200で返る）、サーバ側の処理を置けない。
    2026-08-10、接続した Vercel アカウントで確認しても該当プロジェクトが1件も無く
    （`list_projects` が空、`get_project` も404）、このアカウントからは触れない
    ドメインだと確定した
  - そこで**別プロジェクトとして中継を新規に立てた**（2026-08-10、初代）。
    実機で試したところ、**Supabase直送と一字一句同じ理由
    （`fetch blocked by privacy-gateway`）で新ドメインでも弾かれた。**
    つまり遮断は「ドメインの狙い撃ち」ではなく、**`fetch`/`XMLHttpRequest`
    というAPI自体がページ内でJS層により差し替えられている**ことが確定した
    （`describeEnv()` で `fetch=` `XHR=` の両方が「横取りされています」）
  - そこで中継に**隠しフォーム(iframe)経由の保存**を追加した（2026-08-10）。
    fetch/XHRのJS APIを一切使わず、通常のHTML `<form>` をiframeへPOSTする。
    結果はレスポンス本文を直接読めないので、中継が返すHTMLに仕込んだ
    `<script>` から `postMessage` で伝える。curlとBrowser paneでの単体検証
    （818msで実際のSupabaseエラーが返る）に続き、**2026-08-14、依頼者の
    Android・配偶者のiPhoneの両方で実機確認済み＝解決**。詳細・経緯は
    `docs/HANDOVER_ANDROID_SAVE_ISSUE.md`
  - `tools/collect-core.js` の `SAVE_ENDPOINTS` は各要素に `ways`
    （`["fetch","xhr"]` または中継のみ `["fetch","xhr","iframe"]`）を持ち、
    宛先×対応する手段を総当たりする
  - **Vercelは同じプロジェクトへの2回目以降のデプロイをAPI経由では403で拒否する**
    （複数回再現）。中継を直したら**新しいプロジェクト名で作り直す**しかない。
    いまの本番は `jal-seats-relay2.vercel.app`（初代 `jal-seats-relay` は
    iframe未対応のまま放置。実害なし）
  1回の保存にかける上限は90秒（`SAVE_BUDGET_MS`）。総当たりで何分も粘らない
- **保存は fetch と XHR の両方で試す**。端末によっては**ページの中の `fetch` が
  横取りされていて、第三者ドメインへの通信だけ弾かれる**（実機で
  `<URL> fetch blocked by privacy-gateway` を確認。例外の中身は Error ではなく
  ただの文字列だった＝ページ内で `fetch` が差し替えられている証拠）。
  JALのAPIは同じ `jal.co.jp` なので通り、保存先の `supabase.co` だけが落ちるため、
  **70区間を集めきったところで必ず失敗する**という症状になる。
  横取りされるのは `fetch` だけのことが多いので XHR に落とす。
  一度通った手段は覚えて、次回はそちらを先に使う。
  端末ごとに出る/出ないのは、その端末に入っている拡張・コンテンツブロッカー・
  ブラウザの設定の違い。**サイト側の不具合ではない**
- **保存は3回まで試す**。8〜10分かけた結果を、送信1回のつまずきで捨てないため。
  ただし**待っている間も何をしているか出すこと**。以前は「保存しています…」のまま
  最大3分黙っており、止まったようにしか見えなかった。いまは
  「通常の方法で送信中… 1回目（最大20秒待ちます）」のように手段と回数を出す
- **送信には自前の期限（20秒）を被せている**。fetch も XHR も横取りされている端末では、
  手段側のタイムアウトが効かず黙り込むことがあるため、`Promise.race` で必ず抜ける
- **jsDelivr は @main を最大12時間キャッシュする**。push したら
  **`npm run purge:cdn`** を実行すること。直したはずの不具合が特定の端末だけ
  再現し続けたのがこれ（Vercelに届かない端末が jsDelivr の古いコピーを掴んでいた）。
  失敗時の表示に「版=… / 読込元=…」が出るので、次からはすぐ気づける
- **座席表は50便ごとに区切って保存する**。最後にまとめて保存していたため、途中で
  止まるとその回ぶんが丸ごと消えていた（91/231 で止まって91便ぶんを失った）。
  座席属性の調査ぶん（`codes`）も、最初の区切りの時点で残る
- **空いている座席番号（`sm`）を持ち帰るようにした**（2026-08-09）。座席表を
  取るときの応答に元から `seatNumber` が入っており、いままでは数えるだけで
  捨てていた。追加のJALへの問い合わせはない。`/seats/` の普通席セルを
  クリックすると、窓側/通路側/非常口/足元ゆったりを色分けした一覧が開く。
  満席の席は持たない（「機内の埋まり方」の再現ではなく「空いている席の一覧」）。
- **座席の並びを実際の列幅で描くようにした**（2026-08-09、同日2回目の改修）。
  「左右どちら・通路は何本・翼はどこ」が分かるよう、JAL公式の座席配置図
  （`www.jal.co.jp/jp/ja/aircraft/conf/`）を見て機材ごとの列記号を
  `seats/index.html` の `AIRCRAFT_LAYOUT` に起こした。空いていない列は
  破線のプレースホルダで骨格だけ見せる（実際に満席とは断定しない）。
  主翼の位置は側面図から読み取った目安で、工学的な正確さはない。
  対応機材（`73H`/`767`/`359`/`788`/`E90`）以外は、いままでどおり
  空いている席だけの単純な一覧にフォールバックする。詳細は
  `docs/SEAT_AVAILABILITY.md` の「座席の見た目（機材ごとの列配置）」
  詳細は `docs/SEAT_AVAILABILITY.md` の「座席表の詳細」
- **JALへのリクエストに30秒のタイムアウトを持たせている**。以前は無く、1本ハングすると
  収集全体が先へ進めず、依頼が「進捗が止まったため中断しました」で落ちていた
  （拡張の 8/9 10:04 の収集が座席表 91/231 で実際にこれ）。打ち切れば
  その1便を飛ばして続けられる
- **失敗した枠は自動で消さない**。以前は20秒で消えており、何が起きたか読む前に
  消えて原因が分からなくなっていた。「内容をコピー」ボタンも付けてある
- **ブックマークレットの長さ**。ロジックを埋め込むと2万字を超え、Androidのブックマークで
  切り捨てられて**何も起きなくなる**。いまは `collect.min.js` を読み込むだけの
  約2,500字。この形なら**ロジックを直しても登録し直しは不要**
- **読み込みは `fetch`+`eval` ではなく `<script>` タグ**。`fetch` はレスポンスに
  `Access-Control-Allow-Origin` が要るため、途中の機器やボット対策がヘッダを落とすと
  `Failed to fetch` になる。Androidで「収集スクリプトを取得できませんでした」から
  進まなかったのがこれ。`<script>` なら CORS も `eval` も要らない。
  配信元は Vercel → jsDelivr → GitHub Pages の3つを順に試す
- **jal.co.jp / booking.jal.co.jp は CSP を出していない**（実測）。
  `eval` や外部スクリプトが禁じられているわけではないので、そこを疑わなくてよい
- **1回の収集は2回保存する**（運賃だけ→座席表を足して再保存）。途中で失敗しても運賃分を
  残すためだが、素朴に作ると①前回の座席表が消える ②「前回の値」が自分自身になる。
  収集側が `runId` を送り、Edge Function 側で引き継ぎ処理をしている
- **夜間は全区間が `cancelled` で返る**（最終便まで出発済み）。台風の欠航と区別がつかない
  ので、*全区間 cancelled かつ当日* なら「本日の運航は終了」と表示する。収集側も
  **全区間が `error` のときだけ**セッション拒否とみなす
- **依頼の期限切れは経過時間ではなく「無音時間」で見る**。収集は10便ごとに進捗を書くので、
  `updated_at` が5分止まったら中断とみなす。以前 `requested_at` から10分で切っていて、
  正常な収集が失敗表示になり、連打防止も外れて二重実行が起きた
- **拡張の収集中フラグは storage に置く**。Service Worker は数十秒で止まるので、メモリ上の
  フラグだと再起動後に二重起動する
- **PostgREST の `on_conflict` は部分ユニークインデックスでは効かない**。
  `where run_id is not null` にしていたため履歴の書き込みが黙って失敗していた（修正済み）
- **本番のエンドポイントにテストデータをPOSTしない**。スナップショットは上書きなので、
  実データが飛ぶ（2026-08-09 に実際にやってしまった）
- **`sleep()`のキープアライブは、8/10に見つかった問題の対症療法にすぎなかった。
  同じ危険が残っている箇所を見落としていた（2026-08-15に発覚・修正）。**
  `runJob()`の`await done`（収集完了を待つ、最大20〜40分の待ち）は`chrome.*`APIを
  一切呼ばない「素の待ち」のままで、ここでService Workerが強制終了されていた。
  実データで確認: 直近48時間のHND収集12回のうち11回が、無応答監視の閾値
  （20分＋余裕5分＝25分）ちょうどで強制終了されており、`runJob()`自身の
  catch節（本来なら「収集が時間内に終わりませんでした」等を記録するはず）が
  **一度も発火していなかった**——つまり`await done`内の`setTimeout`ごと
  消えていたことになる。拡張のローカルログ（`chrome.storage.local`の`runLog`、
  Chromeプロファイルの`Local Extension Settings`から直接抽出して確認）に
  「開始（依頼#43）」の次が25分後の「自動復旧: 無応答のため中断」だけで、
  間に何も記録されていないことで裏付けが取れた。
  対策として`await done`にも`sleep()`と同じ15秒間隔のキープアライブを追加した。
  **座席の詳細（`sm`）が長期間更新されていなかった実害の直接原因**
  （`docs/JAL_ONLINE_CORP.md`にも関連の調査記録あり）
- **sessionStorageのキーが「有るかどうか」で画面を見分けてはいけない**
  （2026-08-16）。JALのアプリは起動時に25個ほどのキーをまとめて初期化するので、
  法人（JALオンライン）の目印にしていた `corpData` は**公式のセッションにも
  最初から入っている**（中身は `{"lastName":"","firstName":""}`）。
  「有れば法人」で判定していたため、**スマホからの公式の更新が丸ごと法人モードで
  走り、`hub=JOH` に保存されて空席（`hub=HND`）が更新されなくなっていた**。
  日の選択（今日/明日/両日）が出なくなるのが見た目の兆候。
  いまは押した人に選ばせ、`corpData` の中身とURLはヒントとしてしか使わない。
  **偽ブラウザ（`simulate-collect.mjs`）が実物と違う値を返していたせいで、
  この誤りが検証をすり抜けた**のも教訓。詳細は `docs/JAL_ONLINE_CORP.md`
- **「収集の健康状態」バーは依頼（`?action=recent`）だけを見てはいけない**
  （2026-08-16）。**スマホのブックマークレットは依頼を通さず、その場で
  スナップショットを直接保存する**ので、スマホから更新してもバーの時刻が動かず、
  昼の失敗の警告も出たままになっていた。いまはハブごとに
  「実際に入っているデータの `generatedAt`」と「直近の依頼」を見比べ、
  新しいほうを最後の成功として出す（収集中はそのまま「収集中…」）。
  データは非同期に届くので、空席・制度枠を読み終えた時点で `renderHealth()` を
  呼び直している。前の日のままのときは時刻に日付も添える

## 7. 天気（2026-08-23 追加）

**きっかけ:** 詳細レポートを分析するにあたって「天気が重要なファクターでは」という指摘。
実装前にAPIの実現性だけ先に確かめてから着手した。

### 使ったもの

**Open-Meteo**（`archive-api.open-meteo.com` / `api.open-meteo.com`）。
APIキー不要・無料・CORS開放（`access-control-allow-origin: *` を実測確認）で、
JALの収集で悩まされてきた「fetchがJS層で横取りされる」問題とは無縁
（あちらはJALのページの中で実行するブックマークレット特有の話。天気はサイト自身の
普通の通信）。緯度経度は複数地点をカンマ区切りで渡せば1リクエストでまとめて返る。
空港の緯度経度は `index.html` の `AP`（ルートマップのピン表示用）から写した。

### 置き場所

- **過去の確定日**（詳細レポート用）… Edge Function `?action=weather&airports=&from=&to=`
  が `jal_weather_daily`（airport, date が主キー）にキャッシュする。過去日は値が
  変わらないので、一度取れば以後はDBから返す（2回目の応答は1.9秒→0.37秒に短縮、
  実測済み）。当日はまだ解放中で確定していないため、前日までに切り詰めて扱う
- **当日・翌日の予報**（`/seats/` の路線見出しに表示）… **DBには置かない**。
  サイトが直接 Open-Meteo の予報APIを叩く。値が刻々と変わるものをキャッシュすると
  古い値を返し続けることになるため、あえて経由させていない。
  **一覧の上にまとめて出す形は2026-08-23に一度作ったが、その日のうちに
  「便が並ぶ場所（例: 羽田→新千歳の見出し）に出してほしい」と言われて作り直した。**
  いまは各路線の見出し（`route-head`）に、出発・到着それぞれの空港の天気を
  「☀️30/25℃ ☔2% → ⛅26/20℃ ☔1%」の形で添えている（`wxTag()`）

### ハマりどころ

- **地点が1つだけだと、レスポンスが配列ではなく単体オブジェクトになる。**
  複数地点なら配列で返る。地点数で分岐しないと1空港だけのときに壊れる
  （`missing.length === 1 ? [wx] : wx` で吸収）
- Edge Function の天気アクションは、任意の緯度経度を問い合わせさせないよう
  **許可リスト方式**（`AIRPORT_LL` に無いコードは無視）にしてある。合言葉と違って
  読み取り専用の口だが、任意地点への踏み台にされる余地を残さないため

### 詳細レポートでの見せ方

いまは**羽田の天気だけ**を使って「晴れ/曇り/雨/雪/雷雨」区分・「雨の有無」・
「風の強さ」で制度枠の取れやすさを比べている。相手空港（行き先）側の天気は
まだ使っていない（区間ごと・日ごとの天気を突き合わせるには corp-stats 側の
集計をもう一段細かくする必要があり、まずは効果があるかを見るための最小構成に
した）。データが増えて「天気で効果がありそう」と分かったら、行き先側の天気も
足す価値がある。

### 風速（2026-08-23 追加、同日 km/h → m/s に変更）

「飛行機は雨より横風の影響を受けやすい」という指摘で追加。過去日の
`jal_weather_daily`（`?action=weather` が返す `wind` フィールド。Open-Meteoの
`windspeed_10m_max`）はもともと保存していたので、DB・Edge Functionはほぼ
無改修で詳細レポートに「風の強さ」区分を足せた。

**単位は当初km/hだったが、同日中に本人指定でm/sに変更した。** Open-Meteoは
`&wind_speed_unit=ms` を付けるだけでm/s単位の値を返してくれる
（archive API・forecast APIとも対応）ので、クライアント側で変換する必要は
ない。**既存のキャッシュ（km/hで16行）は単位が混在しないよう全削除して
作り直した**（`truncate table jal_weather_daily`）。過去の確定日データは
再取得すれば同じ値になるので、消して問題ない。

**強風の閾値は15m/s（`WX_WIND_STRONG`）。** 本人指定の値で、根拠のある
数字ではない。傾向が出てきたら見直すこと。

`/seats/` の路線見出しにも、風速と瞬間風速（`windgusts_10m_max`）をm/sで
予報から添えている（小数第1位まで）。閾値以上は色を変えて目立たせる
（`.wxwind.strong`）。

## 8. 検証について

このプロジェクトは**内蔵ブラウザからJALのページ→外部ドメインへの通信が遮断される**環境で
作っている。そのため、**ブックマークレットをJALの実ページで押す最後の一手だけは
毎回こちらで確認できていない**。CORS応答・スクリプトの構文・収集ロジック・表示は
それぞれ個別に実データで確認しているが、通しの実行は利用者側の報告に頼っている。
引き継ぐ場合もこの前提は変わらないので、**「実機で押してもらう」工程を見込んでおくこと**。
