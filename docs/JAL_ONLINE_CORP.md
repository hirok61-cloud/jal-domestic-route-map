## 訂正（2026-08-15）: 「1回検索が必要」は誤りだった

以前は「JOHNにログインしただけでは `apiAuthCreds`（認証トークン）が無く、
1回検索して初めて入る」としていたが、**これは誤り**。改めて検証したところ、

- **新しいタブでJOHNトップを開くだけで、検索せずとも数百ms程度でトークンが入る**
  （`sessionStorage.airBounds`/`airSearchCriteria` が空＝検索の痕跡ゼロの状態で、
  APIを2回叩いて両方とも200・実データが返ることを確認）
- 誤った結論に至った原因は、**前回の検証時にそのタブが1時間以上放置されて
  セッション切れになっていた**ことだった。「検索したら直った」ように見えたのは、
  検索という操作でページが再びアクティブになり、たまたまトークンが作り直された
  だけで、**検索という操作そのものに意味があったわけではない**

**正しい理解:** 検索は不要。ただし**ページを長時間放置するとセッションが切れる**
（無操作で約1時間）のは変わらず正しい。ログインし、企業（ＬＴ００）を選んで
トップページが出ていれば、そのまま実行してよい。

この訂正を受けて、コード（`collect-in-browser.js`・`seats/index.html`）と
以下の記述はすべて直してある。フェーズ1（0時5分の自動実行）の設計も、
日付選択・カレンダー操作・検索ボタン押下という壊れやすいUI自動化が丸ごと不要になり、

**「その便を制度で予約できるかどうか」だけ。** 点数も残席も出さない。

## 制度枠の実際の挙動（本人談・2026-08-14）

**0時の一斉解放だけではない。** 収集の設計はこれに合わせる必要がある。

1. **人気路線は0時台に埋まる**（伊丹＝激戦、新千歳も）。福岡は比較的取れる
2. **残数が少ないと制度枠がそもそも表示されない**（＝予約できない）。
   → **公式の残席（`eco`/`sa`）から予測できる可能性がある。ここが最重要。**
   もし予測できるなら、公式データは JOHNログイン無しで毎日3回集まっているので、
   **自動ログインもパスワード保管も永久に不要になる**
3. **残数が十分でも、搭乗4時間前から徐々に解放される便がある**（新千歳で観測）。
   → **0時5分の断面では原理的に捕まえられない。**
   0時5分だけを土台にしたバッジ表示は、朝の時点で既に誤っていることになるので作らない
   - ただし**お盆（2026-08-14はお盆の最中）の一時的な措置である可能性**がある。
     お盆は8/16頃までなので、**来週の平常時と比べればすぐ分かる**

### 対象路線

**公式と同じ35路線・70区間**（2026-08-15、7路線の抜粋から変更）。
区間が一致していると、公式の日次スナップショット（`hub=HND`・同じ日付）と
便名で突き合わせるときに欠けが出ない。

法人モードは1区間につき法人＋公式の2回叩くので、**1掃引で140リクエスト・約3分**
（座席表を取らないので、公式収集の8〜10分よりは短い）。

### 解析に要る項目は既存データで足りる

搭乗まで何時間かは `dep`（出発時刻）と `generatedAt`（取得時刻）の差で出せる。
1日に数回取れば、同じ便が「12時間前」「6時間前」「3時間前」と複数時点で
観測され、解放カーブが見える。**追加の項目は不要。**

## 実測（2026-08-15 01:10頃・搭乗日 2026-08-15・お盆最終盤）

対象7路線14区間で、**制度枠と公式の残席をペアで取得**した最初のサンプル。公式135便。

### 分かったこと

**1. 返ってくる便は全て予約可能。** 全区間で「取れる N/N便」。
`eco > 0` でない便は最初から返らない。**バッジは「返ってきたか」だけで判定できる。**

**2. 公式の残席だけでは制度枠を予測できない。**

| 公式の残席 | 制度枠あり | 制度枠なし | 出る率 |
|---|---|---|---|
| 9（空席あり） | 64 | 35 | **65%** |
| 8以下 | 5 | 31 | **18%** |

- 「**残数が少ないと出ない**」は裏付けられた（8以下なら18%）
- しかし **`eco=9` でも35%は出ない**。必要条件に近いが十分条件ではない
- → **公式データだけで代替する案は不成立。制度枠そのものを取る価値がある**

**3. 残席より方向の効果が圧倒的に大きい**（この日は帰省ピークの8/15）。

| 羽田発（下り） | | 羽田行き（上り） | |
|---|---|---|---|
| HND-CTS | **17/17** | CTS-HND | 3/17 |
| HND-FUK | 15/17 | FUK-HND | 5/17 |
| HND-AOJ | 6/6 | AOJ-HND | **0/6** |
| HND-HKD | 3/3 | HKD-HND | **0/3** |
| HND-OBO | 4/4 | OBO-HND | 1/4 |
| HND-MYJ | 5/6 | MYJ-HND | 3/6 |
| HND-ITM | **1/15** | ITM-HND | 6/14 |

- `AOJ-HND` / `HKD-HND` は**区間まるごと `JSL001E009`**
- **HND-ITM だけ下りなのに 1/15**。伊丹が激戦という本人談と一致

**4. 混雑方向では早朝便だけが出る。**
`CTS-HND` は残席9の便が14便あるのに、制度枠が出たのは **07:35 / 07:40 / 09:50 の3便だけ**。
`HND-ITM` も **06:30 の1便のみ**。**時間帯が効いている**（「4時間前解放」との関係は未確認）。

**5. 0時台にメンテナンスは無かった**（01:10に正常動作）。

### 運用上わかったこと（設計に直結）

- **無操作のセッションは1時間程度で切れる。**
  切れると検索時に「一定時間操作されなかったか、ブックマークからのアクセスのため
  お取り扱いを続けることができません」と出る。**画面はログイン済みに見えたままなので
  気づきにくい**（APIは `{"message":"User is not authorized..."}` を返す）
  - → **「就寝前にログイン → 0時5分に収集」というフェーズ1の前提は成立しない**
- **`sessionStorage` はタブ単位。** ログイン直後の `john-top` を開くだけで
  トークンは入る（**検索は不要**。2026-08-14時点ではここを誤って「検索が要る」と
  記録していたが、2026-08-15に訂正した。冒頭の「訂正」参照）
- 認証切れの応答は `errors` ではなく `message` を返すので、
  **`describeError` では拾えず「便が0件」に見える**。収集側で `message` を
  認証エラーとして扱う手当てがまだ入っていない（要対応）

## 0時5分の自動実行の設計（2026-08-14 決定）

**2段階で入れる。いきなり自動ログインを作らない。**

### フェーズ1（先に作る）: パスワードを保存しない「セッション温存」方式

- 就寝前などに**利用者が自分でJALオンラインにログインしておく**
- 0時5分に拡張が、**生きているセッションを使って**法人ぶんを収集する
- セッションが切れていたら収集を諦め、Macに通知するだけ
- **パスワード保管もアカウントロックのリスクもゼロ**

**技術的な要点（2026-08-15訂正）: `sessionStorage` はタブ単位だが、
JOHNトップを開くだけでトークンが入る。検索は不要。**
以前はここで「1回検索してトークンを用意する」手当てが要るとしていたが、誤りだった
（冒頭の「訂正」参照）。おかげで、壊れやすい日付ピッカー・カレンダー操作・検索ボタン
押下のUI自動化が丸ごと不要になった。

想定する流れ:

1. `https://booking.jal.co.jp/jl/dom-corp/john-top` を開く
2. `/jl/dom-corp/error` かログイン画面に飛ばされたら**セッション切れ**。
   通知して終了（**ここでパスワードは一切使わない**）
3. 数百ms〜数秒待って `sessionStorage.apiAuthCreds.authToken` が入るのを確認する
4. `collect.js` を `job.hub="JOH"` で注入する

### フェーズ2（フェーズ1が安定してから）: 自動ログイン

置き場所は **`chrome.storage.local`**（既存の合言葉と同じ場所。値は利用者本人が入力）。
**以下は必須:**

- **1回だけ試す。リトライ禁止**
- **サーキットブレーカー**: 1度でも失敗したら自動ログインを永久停止し、
  設定画面で手動解除するまで二度と試さない。**これが無いと、保存値が古く
  なったとき毎晩1回ずつ失敗を積み上げて数日でアカウントがロックする**
- 「パスワードが違う」と「通信断・メンテナンス」を**文言で見分ける**。
  前者だけがブレーカーを落とす
- 保存直後に自動テストしない。**「いま1回だけ試す」ボタン**を置き、
  利用者が見ている前で失敗させる
- SSO画面はReact。`value` の代入だけでは反応しない
  （ネイティブsetter＋`input`イベントが要る）。ここのコードはまだ存在しない

### 決めたこと・保留

- **Macが寝ていたら諦める**（`pmset` での定時起床はしない）。
  起きているときに動けばよい、という判断
- **JALの深夜メンテナンス**が0時台に当たるかは未確認。当たるなら時刻の見直しが要る
- **0時ちょうどに手動で予約を取る場合、70区間の掃引と競合する恐れがある**。
  掃引中は予約操作をしない運用にする

## 学習フェーズの作り（2026-08-15 実装）

**目的は「制度枠が出る便と出ない便の違い」を突き止めること。** 表示や自動ログインより先に、
まずデータを貯める。

### 使い方

1. **JALオンラインにログインし、企業（ＬＴ００）を選んでおく**（検索は不要）
2. `/seats/` の **「制度枠を記録」ボタン**（紺色）を押す
3. 約3分で70区間ぶんが `hub=JOH` に記録される

**0時5分にこだわらない。** 法則を学ぶだけなら朝でよく、そのほうが手動ログインの
負担が現実的（無操作セッションは1時間で切れるので、0時台の手動運用は無理）。

### 保存される形

`routes[].flights[]` は**公式の全便**。各便に `zl`（その時点で制度で予約できたか）が付く。
出た便と出なかった便が同じ表に並ぶので、そのまま分析に使える。

- 法人と公式を**同じ瞬間に**取る（1区間2リクエスト）。別々に取ると数時間ずれ、
  実搭乗率が変わってしまうため
- **座席表（`sa`/`st`）は取らない**。公式の日次収集（`hub=HND`・同じ日付）に
  入っているので、**便名で後から突き合わせる**。`eco` は9が上限で粗いため、
  「残席9の便のうち65%しか出ない」を割るには `sa/st` の実搭乗率が要る

### セッション切れの検知

認証切れは `errors` ではなく **`message`** で返る（`User is not authorized...`）。
拾わないと「便が0件」に見え、**空のまま毎日記録し続ける**ことになる。
1区間目で検知して即中止するようにした（テスト済み）。

## スマホ対応（2026-08-15 実装）

**ブックマークレットも法人モードに対応した。** ただし「公式／法人」を毎回聞くのではなく、
**開いているページで自動判定する。**

判定は `sessionStorage.getItem("corpData")` の有無で行う。
検索結果ページ（`/jl/dom-bkg/upsell`）は公式・法人どちらも同じパスに来るので
URLでは見分けがつかないが、**JOHNログインを経由したセッションだけがこのキーを持つ**
（公式の検索フローはここに触れない）。法人と判定したら、「今日/明日/両日」を聞く
画面は出さずに今日固定で始まる（制度枠は当日ぶんしか解放されないため）。

使い方は基本形と同じ: JALオンラインにログインし、企業（ＬＴ００）を選んだ状態で
ブックマークレットを呼び出す（検索は不要）。保存先・合言葉の仕組みは公式版と共通。

最初は「制度枠の記録を見る」という別リンク＋パネルにしていたが、**見づらいという

## PCから「制度枠を記録」が失敗する不具合（2026-08-15 発見・修正）

**原因: `background.js`（拡張の裏方）に、法人ジョブ用の分岐が丸ごと抜けていた。**
`collect-core.js`/`collect-extension.js`（何を検索するか）は法人モードに対応させたが、
**どのタブで検索するか を決める `background.js` の `runJob()` を直し忘れていた。**
`hub=JOH` の依頼を拾っても、これまでどおり新しいウィンドウを開いて**公式サイト**
（www.jal.co.jp）に行き、そこに法人フラグ付きのリクエストを送っていた。
ユーザーが別タブでJALオンラインにログイン済みでも、拡張はそのタブを一切見ていなかった。

実データで確認済み（拡張のローカルログより）:
```
7:28:30  開始（依頼#44）
7:29:16  失敗: JALに接続を断られています（Required Input not available）。
         JALオンラインを開き直してから、もう一度実行してください。
```

**修正:** `runJob()` に `job.hub === CORP_HUB` の分岐を追加。新規ウィンドウは開かず、
**既に開いているタブの中から、JALオンラインにログイン済みのもの
（`sessionStorage.corpData` で判定。ブックマークレットと同じロジック）を探して
そこへ注入する**ように変更した（`findCorpTab()`）。見つからなければ
「JALオンラインにログインしたタブが見つかりません」と明確に案内して止める。
自動ログインが無い以上、ユーザーがどこかのタブでログインしていることが前提。

## 座席の詳細が長期間更新されていなかった重大バグ（2026-08-15 発見・修正）

**これは制度枠と無関係の、既存の空席収集（`hub=HND`）そのものの障害だった。**
詳細は `docs/HANDOVER.md` の「5. ハマったところ」参照。要約:

- 朝7時の自動更新で座席詳細（`sm`）が更新されておらず、`sa`/`st` も
  8/13〜8/14の古い値が引き継がれているだけだった
- Supabaseの依頼ログを見ると、直近48時間のHND収集12回のうち**11回**が
  「拡張のバックグラウンド処理が途中で止まりました」で失敗。しかも毎回
  ほぼ正確に25分（無応答監視の閾値）で強制終了されていた
- 拡張のローカルログ（`chrome.storage.local`の`runLog`）を直接読むと、
  `runJob()`自身のcatch節が一度も発火していなかった＝`await done`
  （収集完了を待つ最大20〜40分の待ち）内の`setTimeout`ごとService Workerが
  消えていたと判明
- `sleep()`には2026-08-10の教訓からキープアライブ（15秒おきに`chrome.*`APIを
  呼んでService Workerを起こし続ける）が入っていたが、**いちばん長く待つ
  `await done`にだけ同じ対策が入っていなかった。** 追加して修正
- Macのシステムスリープは`pmset -g log`で確認し、該当時間帯は原因から除外できた

**両方の修正とも、Chromeの拡張を再読み込み（`chrome://extensions` の再読み込み
ボタン）しないと反映されない。**

## データを貯める土台（2026-08-15）

**制度枠は記録しても翌日には消えていた。** `jal_prune_old_snapshots()` が
`flight_date < 前日` のスナップショットをハブに関係なく全削除しており、
JOHもその対象だった。中長期の傾向分析（何割取れるか、どの路線が厳しいか）は
日々の蓄積が前提なので、これでは永久に貯まらない。

**ハブごとに保持期間を分けた**（DB関数の差し替えのみ。**Edge Functionには触っていない**
——本番の実装がリポジトリ版と差異があり、再デプロイが危険なため）:

- `hub <> 'JOH'`（空席）… これまでどおり前日ぶんまで。表示にしか使わないため
- `hub = 'JOH'`（制度枠）… **400日**保持。1日あたり約49KBなので400日で約20MB

### レポートを作るときの注意（未実装）

- **`?action=all&hub=JOH` は過去日を返さない。** Edge Function 側で
  `flight_date >= 今日` に絞っているため。過去日は `GET /?hub=JOH&date=YYYY-MM-DD`
  を日付ぶん呼ぶ必要がある（30日なら30リクエスト。Edge Functionを触らずに済む）
- **1日1行しか残らない。** スナップショットは `(hub, 搭乗日)` で上書きなので、
  同じ日に複数回記録しても最後の1回だけが残る。日次の粒度では十分だが、
  「搭乗4時間前から徐々に解放される」ような日内の変化は追えない。
  日内の変化まで見たいなら、別途1日複数行を残す仕組みが要る
