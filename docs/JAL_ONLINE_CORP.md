## いつ何が返るか（この機能の肝）

**制度枠は当日ぶんしか出ない。日付が変わる瞬間に翌日ぶんが開く。**
2026-08-14 21:00〜22:00 に実測したところ、成功レスポンスを得られる時間帯が無かった:

| 対象日 | 返るもの | 意味 |
|---|---|---|
| 当日（8/14） | `JSL001E006` "Flights Scheduled but all are cancelled" | 最終便まで出発済み。公式サイト版と同じ挙動（`docs/SEAT_AVAILABILITY.md` 参照） |
| 翌日（8/15〜) | `JSL001E009` "No flights due to fare and route constrain" | **まだ解放されていない**。この契約で取り扱いのある運賃が無い |

羽田発の主要4路線（ITM / CTS / OKA / FUK）すべてで同じだった。

- `JSL001E006` … 当日の運航終了。**エラーではない**
- `JSL001E009` … その日・その区間はこの契約の対象外。**これが「予約できる便だけ表示」の実体**
  （UI上も「ご予約可能な運賃が表示されております」と出て一覧が空になる）

→ **0時5分に当日ぶんを取る**という設計は、この解放タイミングと合っている。

## 何を表示するか（2026-08-14 決定）

**「その便を制度で予約できるかどうか」だけ。** 点数も残席も出さない。

そのため**成功レスポンスの中身をほとんど知らなくてよい**（当初は必要点数の位置を
調べるつもりだったが、要件が○×だけなので不要になった）。制度で買える便だけが
返ってくるので、**返ってきた便＝予約できる便**（`eco > 0`）として扱えばよい。

なお ＬＴ００ は点数制（資格点数を使う）。金額ではない。

## 実装（2026-08-14）

収集ロジックは既存の1本（`tools/collect-core.js`）に**法人モードを足す形**にした。
コピーを増やさないという既存方針どおり。

- `createRun({ corporate: true })` で法人として動く
  - 検索条件が `{discountCode:"NONE", isCorporate:true}` に変わる
  - **座席表を取らない**（○×の判断に要らず、1便2.3秒かかるため）
  - 保存先のハブが `CORP_HUB`（`"JOH"`）になる
- **`JSL001E009` を `empty` に分類することが必須**（`describeError`）。
  法人では70区間の大半がこれを返すため、`error` に分類すると
  「3区間続けて error ならセッション拒否」の安全弁に引っかかって毎回中断する。
  既存コードは偶然 `no flight` の判定で empty になっていたが、意味が違うので明示した
- 保存は**ハブ名を分けるだけ**で既存の空席データと混ざらない。
  **テーブルもEdge Functionも変更していない**（本番のEdge Functionはリポジトリ版と
  細部が違い、再デプロイすると巻き戻る危険があるため。`docs/SEAT_AVAILABILITY.md` 参照）。
  取り出しは `?action=all&hub=JOH`

`npm run build:bookmarklet` / `npm run test:collect` は通済み（既存4シナリオとも変化なし）。

## 入口の配線（2026-08-14 実装）

**依頼の `hub` で分けるだけで済んだ。サーバ側の変更は不要。**
依頼テーブルは前から `hub` を端から端まで運んでいる
（`?action=request&hub=JOH` で積む → `?action=claim` が `job.hub` で返す →
`background.js` が `job` をそのまま `chrome.storage.local` に置く）。

`tools/collect-extension.js` が `job.hub === CORP_HUB` を見て法人モードで走る。
あわせて**法人では翌日を見に行かない**（制度枠は当日ぶんしか出ないため）。

### 空の結果で上書きしない安全弁（課題だったところ）

法人モードで1便も見つからない状態は、次の区別がつかない:

- (a) JALオンラインにログインしていない
- (b) ログインしたが企業（ＬＴ００）を選んでいない
- (c) 本当にその日の制度枠がゼロ

(a)(b) でも全区間が `JSL001E009` になるとみられ、そのまま保存すると
「予約できる便は無い」と表示され続ける。そこで**1便も無ければ保存せずに止める**
（既存の「全区間 error なら保存しない」と同じ考え方）。
**(c) が実際に起きうるなら見直すこと。** 実データを見て判断する。

### セッションについて（実測）

**JOHNのセッションからは公式運賃の検索も通る**（`{discountCode:"JCF",isCorporate:false}`
で168KBの実データが返ることを確認）。逆は不可。
つまりJOHNにログインしていれば公式ぶんも法人ぶんも同じセッションで取れる。
セッションは少なくとも35分は保った。

### テスト

`tools/simulate-collect.mjs` に拡張限定の2ケースを追加済み。

- 大半が `JSL001E009` でも完走し、70区間・座席表0回・保存1回・ハブ `JOH` になる
- 1便も無いときは保存せず、ログインを促す理由を出して失敗する

## 制度枠の実際の挙動（本人談・2026-08-14）

**0時の一斉解放だけではない。** 収集の設計はこれに合わせる必要がある。

1. **人気路線は0時台に埋まる**（伊丹＝激戦、新千歳も）。福岡は比較的取れる
2. **残数が少ないと制度枠がそもそも表示されない**（＝予約できない）。
   → **公式の残席（`eco`/`sa`）から予測できる可能性がある。ここが最重要。**
   もし予測できるなら、公式データは JOHNログイン無しで毎日3回集まっているので、
   **自動ログインもパスワード保管も永久に不要になる**
3. **残数が十分でも、搭乗4時間前から徐々に解放される便がある**（新千歳で観測）。
   → **0時5分の断面では原理的に捕まえられない。**
   0時5分だけを土台にしたバッジ表示は、朝の時点で既に誤っていることになるので作らない
   - ただし**お盆（2026-08-14はお盆の最中）の一時的な措置である可能性**がある。
     お盆は8/16頃までなので、**来週の平常時と比べればすぐ分かる**

### 対象路線

**公式と同じ35路線・70区間**（2026-08-15、7路線の抜粋から変更）。
区間が一致していると、公式の日次スナップショット（`hub=HND`・同じ日付）と
便名で突き合わせるときに欠けが出ない。

法人モードは1区間につき法人＋公式の2回叩くので、**1掃引で140リクエスト・約3分**
（座席表を取らないので、公式収集の8〜10分よりは短い）。

### 解析に要る項目は既存データで足りる

搭乗まで何時間かは `dep`（出発時刻）と `generatedAt`（取得時刻）の差で出せる。
1日に数回取れば、同じ便が「12時間前」「6時間前」「3時間前」と複数時点で
観測され、解放カーブが見える。**追加の項目は不要。**

## 実測（2026-08-15 01:10頃・搭乗日 2026-08-15・お盆最終盤）

対象7路線14区間で、**制度枠と公式の残席をペアで取得**した最初のサンプル。公式135便。

### 分かったこと

**1. 返ってくる便は全て予約可能。** 全区間で「取れる N/N便」。
`eco > 0` でない便は最初から返らない。**バッジは「返ってきたか」だけで判定できる。**

**2. 公式の残席だけでは制度枠を予測できない。**

| 公式の残席 | 制度枠あり | 制度枠なし | 出る率 |
|---|---|---|---|
| 9（空席あり） | 64 | 35 | **65%** |
| 8以下 | 5 | 31 | **18%** |

- 「**残数が少ないと出ない**」は裏付けられた（8以下なら18%）
- しかし **`eco=9` でも35%は出ない**。必要条件に近いが十分条件ではない
- → **公式データだけで代替する案は不成立。制度枠そのものを取る価値がある**

**3. 残席より方向の効果が圧倒的に大きい**（この日は帰省ピークの8/15）。

| 羽田発（下り） | | 羽田行き（上り） | |
|---|---|---|---|
| HND-CTS | **17/17** | CTS-HND | 3/17 |
| HND-FUK | 15/17 | FUK-HND | 5/17 |
| HND-AOJ | 6/6 | AOJ-HND | **0/6** |
| HND-HKD | 3/3 | HKD-HND | **0/3** |
| HND-OBO | 4/4 | OBO-HND | 1/4 |
| HND-MYJ | 5/6 | MYJ-HND | 3/6 |
| HND-ITM | **1/15** | ITM-HND | 6/14 |

- `AOJ-HND` / `HKD-HND` は**区間まるごと `JSL001E009`**
- **HND-ITM だけ下りなのに 1/15**。伊丹が激戦という本人談と一致

**4. 混雑方向では早朝便だけが出る。**
`CTS-HND` は残席9の便が14便あるのに、制度枠が出たのは **07:35 / 07:40 / 09:50 の3便だけ**。
`HND-ITM` も **06:30 の1便のみ**。**時間帯が効いている**（「4時間前解放」との関係は未確認）。

**5. 0時台にメンテナンスは無かった**（01:10に正常動作）。

### 運用上わかったこと（設計に直結）

- **無操作のセッションは1時間程度で切れる。**
  切れると検索時に「一定時間操作されなかったか、ブックマークからのアクセスのため
  お取り扱いを続けることができません」と出る。**画面はログイン済みに見えたままなので
  気づきにくい**（APIは `{"message":"User is not authorized..."}` を返す）
  - → **「就寝前にログイン → 0時5分に収集」というフェーズ1の前提は成立しない**
- **`sessionStorage` はタブ単位。** ログイン直後の `john-top` にはまだトークンが無く、
  **1回検索して初めて `apiAuthCreds` が入る**。収集前のこの工程は必須
- 認証切れの応答は `errors` ではなく `message` を返すので、
  **`describeError` では拾えず「便が0件」に見える**。収集側で `message` を
  認証エラーとして扱う手当てがまだ入っていない（要対応）

## 0時5分の自動実行の設計（2026-08-14 決定）

**2段階で入れる。いきなり自動ログインを作らない。**

### フェーズ1（先に作る）: パスワードを保存しない「セッション温存」方式

- 就寝前などに**利用者が自分でJALオンラインにログインしておく**
- 0時5分に拡張が、**生きているセッションを使って**法人ぶんを収集する
- セッションが切れていたら収集を諦め、Macに通知するだけ
- **パスワード保管もアカウントロックのリスクもゼロ**

**技術的な要点: `sessionStorage` はタブ単位。**
ログイン済みでもサーバ側のセッション（Cookie）が生きているだけで、
**新しく開いたタブには `apiAuthCreds` が無い**。公式版が `prepare.js` で
1回検索してトークンを用意しているのと同じ手当てが法人側にも要る。

想定する流れ:

1. `https://booking.jal.co.jp/jl/dom-corp/john-top` を開く
2. `/jl/dom-corp/error` かログイン画面に飛ばされたら**セッション切れ**。
   通知して終了（**ここでパスワードは一切使わない**）
3. 開けたら日付=当日で1回検索し、`sessionStorage.apiAuthCreds` を用意する
   （日付欄・カレンダー・確定ボタンの操作は「調査のやり方」の項を参照）
4. `collect.js` を `job.hub="JOH"` で注入する

### フェーズ2（フェーズ1が安定してから）: 自動ログイン

置き場所は **`chrome.storage.local`**（既存の合言葉と同じ場所。値は利用者本人が入力）。
**以下は必須:**

- **1回だけ試す。リトライ禁止**
- **サーキットブレーカー**: 1度でも失敗したら自動ログインを永久停止し、
  設定画面で手動解除するまで二度と試さない。**これが無いと、保存値が古く
  なったとき毎晩1回ずつ失敗を積み上げて数日でアカウントがロックする**
- 「パスワードが違う」と「通信断・メンテナンス」を**文言で見分ける**。
  前者だけがブレーカーを落とす
- 保存直後に自動テストしない。**「いま1回だけ試す」ボタン**を置き、
  利用者が見ている前で失敗させる
- SSO画面はReact。`value` の代入だけでは反応しない
  （ネイティブsetter＋`input`イベントが要る）。ここのコードはまだ存在しない

### 決めたこと・保留

- **Macが寝ていたら諦める**（`pmset` での定時起床はしない）。
  起きているときに動けばよい、という判断
- **JALの深夜メンテナンス**が0時台に当たるかは未確認。当たるなら時刻の見直しが要る
- **0時ちょうどに手動で予約を取る場合、70区間の掃引と競合する恐れがある**。
  掃引中は予約操作をしない運用にする

## 学習フェーズの作り（2026-08-15 実装）

**目的は「制度枠が出る便と出ない便の違い」を突き止めること。** 表示や自動ログインより先に、
まずデータを貯める。

### 使い方

1. **JALオンラインにログインし、1回検索しておく**（これをしないと認証トークンが無い）
2. `/seats/` の **「制度枠を記録」ボタン**（紺色）を押す
3. 約40秒で14区間ぶんが `hub=JOH` に記録される

**0時5分にこだわらない。** 法則を学ぶだけなら朝でよく、そのほうが手動ログインの
負担が現実的（無操作セッションは1時間で切れるので、0時台の手動運用は無理）。

### 保存される形

`routes[].flights[]` は**公式の全便**。各便に `zl`（その時点で制度で予約できたか）が付く。
出た便と出なかった便が同じ表に並ぶので、そのまま分析に使える。

- 法人と公式を**同じ瞬間に**取る（1区間2リクエスト）。別々に取ると数時間ずれ、
  実搭乗率が変わってしまうため
- **座席表（`sa`/`st`）は取らない**。公式の日次収集（`hub=HND`・同じ日付）に
  入っているので、**便名で後から突き合わせる**。`eco` は9が上限で粗いため、
  「残席9の便のうち65%しか出ない」を割るには `sa/st` の実搭乗率が要る

### セッション切れの検知

認証切れは `errors` ではなく **`message`** で返る（`User is not authorized...`）。
拾わないと「便が0件」に見え、**空のまま毎日記録し続ける**ことになる。
1区間目で検知して即中止するようにした（テスト済み）。

## スマホ対応（2026-08-15 実装）

**ブックマークレットも法人モードに対応した。** ただし「公式／法人」を毎回聞くのではなく、
**開いているページで自動判定する。**

判定は `sessionStorage.getItem("corpData")` の有無で行う。
検索結果ページ（`/jl/dom-bkg/upsell`）は公式・法人どちらも同じパスに来るので
URLでは見分けがつかないが、**JOHNログインを経由したセッションだけがこのキーを持つ**
（公式の検索フローはここに触れない）。法人と判定したら、「今日/明日/両日」を聞く
画面は出さずに今日固定で始まる（制度枠は当日ぶんしか解放されないため）。

使い方は基本形と同じ: JALオンラインにログインし、企業（ＬＴ００）を選んで1回検索した
状態でブックマークレットを呼び出す。保存先・合言葉の仕組みは公式版と共通。

## 簡易表示（2026-08-15 実装）

`/seats/` に**「制度枠の記録を見る」リンク**を追加した。押すと `hub=JOH` の最新スナップショットを
取ってきて、取得時刻・全体の予約可能数・路線別の内訳（予約できた率が低い順）を表示する。

**常時表示のバッジにはしていない。** 押したときだけ取得時刻つきで見せる、点検表に近い扱い。
理由は変わらず: 搭乗数時間前から徐々に解放される便があるため、断面を常設のバッジにすると
「もう古い」記録を現在の状況と誤解させる。パネルにもその旨を明記している。

## 残っていること

1. **法人ぶんの依頼を積む導線**。いまは `hub=JOH` の依頼を積む口が無い
   （サイトのボタンか拡張のポップアップに足す）。仕組み自体はできている
2. **`/seats/` のバッジ表示**。`?action=all&hub=JOH` を取って便名で突き合わせる
3. **自動ログインと0時5分の定時実行**（`extension/`）。
   ログインは1回だけ試し、失敗したら即中止・通知。**再試行は絶対に入れない**
4. ブックマークレット側の法人モード（優先度低。スマホでJOHNを使う場面は薄い）

## 調査のやり方（再現手順）

1. `https://booking.jal.co.jp/jl/corp-john/login/member-login-user-before-process?lang=ja` からログイン
   （**深いURLの直叩きは `/jl/dom-corp/error` に飛ぶ**。必ずこの入口から）
2. 企業リストで `G0000001` を選び `button[name="nextbutton"]`
3. `/jl/dom-corp/john-top` で日付を選ぶ。日付欄は `[id*="departureDate"]`、
   カレンダーは `.cdk-overlay-pane.cal-dialog` の `.ngb-dp-day`。
   **`aria-label` が同じセルが隣接月にもある**ので `disabled`/`hidden` を除外する。
   確定ボタンはテキスト完全一致では拾えない（子要素を持つ）ので座標クリックが確実
4. 検索後 `/jl/dom-bkg/upsell` で日付タブを押すと `air-bounds` が飛ぶ。
   `window.fetch` を包めばリクエスト本文・レスポンスを採取できる
